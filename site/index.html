SPECIMEN 01 · LAYER — INTERACTION & MOTION

Scrollytelling스크롤이 카메라를 움직인다

스크롤 위치를 타임라인의 재생 헤드로 쓰는 기법. GSAP ScrollTrigger의 pin으로 화면을 고정하고 scrub으로 진행도를 카메라·오브젝트·DOM 텍스트에 동시에 묶는다. 아래 구간에서 스크롤은 페이지 이동이 아니라 3D 카메라의 돌리(dolly) 조작이 된다.

PHASE 1하나의 타임라인이 카메라 위치를 소유한다

PHASE 2같은 타임라인이 DOM 텍스트도 소유한다 — 이 자막처럼

PHASE 3셰이더 uniform까지 묶으면 장면 전체가 하나의 악보가 된다

0% SCRUB
ENGINE

COST
메인 스레드 · 트리거 수에 비례
FALLBACK
reduced-motion → 정적 프레임

네이티브

GSAP의 본성은 타임라인이다. 카메라 좌표, 오브젝트 회전, 셰이더 uniform, DOM opacity, 사운드 볼륨까지 종류가 다른 값들을 하나의 시간축에 묶는 것 — 이것이 다른 도구가 흉내 내기 어려운 GSAP의 고유 영역이다.

리스크

타임라인이 커지면 수정이 어렵고, 섹션마다 ScrollTrigger를 무분별하게 만들면 성능이 무너진다. React와 함께 쓸 때는 중복 실행과 정리(cleanup)가 단골 사고 지점. 그리고 모든 것을 스크롤에 묶으면 정보 위계가 사라진다 — 표본 13 참조.

응용 케이스

제품 분해 시퀀스(Apple AirPods Pro), 브랜드 스토리 챕터 전환(Igloo Inc), 데이터 저널리즘의 단계별 연출(The Pudding), 포트폴리오 씬 전환. 15~60초짜리 카메라 연출이 많아지면 Theatre.js 같은 키프레임 에디터 병행을 검토한다.

SUB-SPECIMEN · LENIS

지금 이 페이지의 스크롤 감각은 Lenis가 보간 중이다. 네이티브 스크롤을 대체하는 게 아니라 80% 네이티브 + 20% 보간이 권장 강도. 아래 버튼으로 차이를 몸으로 비교해보라. (모바일·reduced-motion에서는 자동 비활성화된다 — 그것도 이 기술의 올바른 사용법이다.)

SPECIMEN 02 · LAYER — VISUAL RENDERING

Custom Shader"그 사이트만의 느낌"의 출처

몰입형 사이트의 고유한 질감은 대부분 프래그먼트 셰이더에서 나온다. 셰이더는 모든 픽셀에서 동시에 실행되는 작은 프로그램이고, 재료는 좌표·시간·노이즈·포인터뿐이다. 아래 표본을 문질러 보라 — 포인터 속도가 uniform으로 흘러 들어가 유체처럼 왜곡된다. 클릭하면 dissolve 전환.

MOVE TO DISTORT · CLICK TO DISSOLVE

ENGINE
Three.js ShaderMaterial (GLSL)
COST
fragment-bound · 해상도에 비례
FALLBACK
WebGL 불가 → 정적 그라디언트

네이티브

GPU는 픽셀 하나하나를 병렬로 계산한다. 그래서 셰이더의 native는 필드(field) — 좌표를 받아 색을 돌려주는 수학 함수다. noise, fresnel, refraction, dissolve 전부 이 함수의 변주. 언어는 WebGL이면 GLSL, WebGPU면 WGSL, Three.js 신규 프로젝트라면 양쪽으로 변환되는 TSL을 검토한다.

리스크

셰이더 오류는 브라우저·GPU마다 다르게 나타난다. 모바일은 fragment 처리량이 낮아 화면 전체 셰이더가 발열의 주범이 되기 쉽다. 해상도(DPR) 상한과 텍스처 샘플 수 관리가 실전의 절반이다.

응용 케이스

이미지 호버 왜곡, 페이지 전환 dissolve, 히어로 배경의 gradient field, 텍스트 리빌의 노이즈 마스크, 유리 굴절(refraction) 카드. 무거운 3D 모델 없이 평면 + 셰이더만으로 공간감을 내는 2.5D가 2026년의 주류 트렌드다.

SPECIMEN 03 · LAYER — VISUAL RENDERING

Particles개체가 아니라 시스템을 설계한다

수천 개의 점 각각에 규칙(노이즈 흐름 + 커서 반발력)을 주면, 완성된 영상이 아니라 실시간으로 실행되는 브랜드 규칙이 된다. 커서를 넣어 보라 — 지금 기기 티어에 맞춰 파티클 수가 자동 조절되어 있다(HUD 참조).

— POINTS · CURSOR = FORCE FIELD

ENGINE
Three.js Points + vertex shader
COST
수만 개까지 WebGL로 충분 · 수십만~수백만은 WebGPU Compute의 영역
FALLBACK
low tier → 개수 1/4 축소

네이티브

파티클의 native는 인스턴싱 — 같은 정점 프로그램을 N개의 점에 병렬 적용하는 것이다. CPU에서 점을 하나씩 움직이면 수천 개가 한계지만, 위치 계산을 vertex shader로 옮기면 자릿수가 달라진다. 그 다음 자릿수(백만 단위)가 필요할 때 비로소 WebGPU Compute Shader가 등장한다.

리스크

파티클 수는 곧 배터리다. "고급 PC에서 60fps"는 의미가 없고 중급 안드로이드에서 측정해야 한다. 매 프레임 CPU에서 배열을 갱신해 GPU로 다시 올리는 구현은 AI 생성 코드의 단골 실수.

응용 케이스

브랜드 키비주얼(로고가 입자로 흩어졌다 모이는 연출), 데이터 포인트 시각화, 커서 트레일, 텍스트→입자 전환. Gaussian Splatting도 본질은 "점 수백만 개를 찍는 것"이라 이 표본의 연장선에 있다.

SPECIMEN 04 · LAYER — INTERACTION & MOTION

Kinetic Type글자는 DOM에 남긴 채 움직인다

텍스트를 Canvas에 그리는 순간 접근성과 SEO를 잃는다. 정답은 진짜 HTML 텍스트를 글자 단위로 쪼개(SplitText 계열) transform만 애니메이션하는 것. 아래 문장은 실제 선택 가능한 DOM 텍스트다 — 스크롤에 따라 글자들이 조판된다.

몰입은 기술이 아니라 시간 설계다

Typography is the interface

글자가 움직여도 문서는 문서로 남아야 한다

ENGINE
DOM split + GSAP stagger
COST
글자 수 = 노드 수 · transform/opacity만 쓰면 저렴
FALLBACK
reduced-motion → 즉시 표시

네이티브

브라우저는 transform과 opacity를 컴포지터에서 처리한다 — 레이아웃 재계산 없이. 그래서 키네틱 타이포의 native는 "글자를 span으로 감싸고 transform만 건드리기"다. width, top 같은 레이아웃 속성을 애니메이션하는 순간 성능 등급이 떨어진다. GSAP SplitText는 3.13부터 무료가 되었다.

리스크

수백 글자를 동시에 stagger하면 노드 수가 폭발한다. 스크린리더가 쪼개진 글자를 읽지 않도록 원문에 aria-label을 남기는 것이 필수 매너. 한글은 조합 문자라 자소 분리 연출은 신중하게.

응용 케이스

히어로 헤드라인 등장, 챕터 제목 리빌, 마퀴(marquee) 스트립, 호버 시 글자 교체. 여기에 셰이더를 더하면(텍스트를 텍스처로 구워 왜곡) 표본 02와 합성된다.

SPECIMEN 05 · LAYER — VISUAL RENDERING

SVG선이 스스로를 그린다

SVG는 DOM처럼 제어되는 벡터다. stroke-dashoffset 하나로 "선이 그려지는" 연출이 되고, path의 좌표를 보간하면 형태가 morph된다. 아래 다이어그램은 스크롤 진행도에 따라 제도(製圖)되듯 그려진다.

ENGINE
SVG + stroke-dashoffset + path 보간
COST
CPU 렌더 · 수천 노드부터 병목
FALLBACK
불필요 — SVG는 어디서나 그려진다

네이티브

SVG의 native는 기하학이 곧 마크업이라는 점이다. path는 검사 가능하고, 접근성 트리에 올라가고, 벡터라 어떤 해상도에서도 선명하다. 선 드로잉은 전체 길이 (getTotalLength)를 dash로 걸고 offset을 줄이는 단순한 트릭.

리스크

SVG는 GPU가 아니라 CPU 래스터라이저의 영역. 노드 수천 개를 매 프레임 움직이면 바로 병목이 온다. 복잡한 morph는 정점 수를 맞춰야 해 제작 비용이 숨어 있다.

응용 케이스

로고 스트로크 애니메이션, 프로세스 다이어그램의 순차 드로잉, 인터랙티브 지도, 커서를 따라 휘는 언더라인. Lottie/Rive가 하는 일의 상당수는 "잘 조직된 SVG 연출"이다.

응용 케이스

텍스트 위주 사이트의 패럴랙스, 이미지 리빌, 다크/라이트 전환, 페이지 전환 (View Transitions API). 먼저 CSS로 되는지 묻고, 안 될 때 Canvas로 올라가는 것이 2026년의 올바른 순서다.

SPECIMEN 08 · LAYER — INTERACTION & MOTION

Fake Physics진짜 물리보다 나은 거짓말

브랜드 사이트에서 필요한 건 정확한 충돌 계산이 아니라 살아있는 느낌이다. 스프링 + 감쇠(damping) + 노이즈면 충분하고, 통제는 훨씬 쉽다. 아래 오브들을 던져 보라 — Rapier 같은 물리 엔진 없이 수식 몇 줄로 움직인다.

SPRING
DAMP
NOISE

DRAG & RELEASE · k=0.06 · damping=0.86

ENGINE
수식 직접 구현 (spring–damper)
COST
무시 가능 · 물리 엔진 대비 1/100
FALLBACK
reduced-motion → 즉시 복귀

네이티브

스프링의 native는 v += (target − pos) · k; v *= damping; pos += v — 이 세 줄이 전부다. 관성, 오버슈트, 되튐이 공짜로 나온다. 진짜 물리 엔진(Rapier)은 충돌·스태킹·캐릭터가 필요할 때만 부른다.

리스크

프레임레이트에 따라 감쇠가 달라지는 구현(delta time 미보정)이 흔한 함정. 진짜 물리 엔진을 쓰면 물리 루프와 렌더 루프의 동기화, 모바일 CPU 비용이 새 문제로 들어온다.

응용 케이스

커서 팔로워, 자석 버튼(magnetic button), 드래그 카드, 메뉴의 탄성 등장, 이미지의 관성 패럴랙스. "Direct Manipulation" 트렌드 — 사용자가 관람자가 아니라 장면에 개입하게 만드는 핵심 재료다.

SPECIMEN 09 · LAYER — INTERACTION & MOTION

Audio Reactive소리가 비주얼을 연주한다

Web Audio API의 AnalyserNode는 재생 중인 소리의 주파수 스펙트럼을 매 프레임 돌려준다. 그 배열을 셰이더 uniform이나 도형 크기에 꽂으면 비주얼이 음악을 연주한다. 브라우저 정책상 소리는 반드시 사용자의 클릭으로만 시작된다 — 그래서 버튼이 있다.

ENGINE
Web Audio API (OscillatorNode + AnalyserNode)
COST
오디오 스레드 별도 · 분석은 저렴
FALLBACK
Sound Off가 기본값 — 이것이 폴백

네이티브

Web Audio의 native는 노드 그래프다. 오실레이터 → 필터 → 게인 → 아날라이저 → 출력으로 신호가 흐르고, 어느 지점이든 탭해서 데이터를 읽을 수 있다. 이 표본의 신스도 mp3가 아니라 오실레이터 노드로 실시간 합성된 것.

리스크

자동재생 차단, 업무 환경에서의 거부감, 접근성, 모바일 배터리. 권장 UX는 명확하다 — Sound Off 기본 + 명시적 On 버튼 + 설정 기억 + 시각적 대체.

응용 케이스

뮤지션·레이블 사이트, 제품 사운드 디자인 쇼케이스, 스크롤 위치에 반응하는 앰비언트 레이어, 클릭·호버의 미세 효과음. 시각 반응은 표본 02·03과 바로 합성된다.

SPECIMEN 10 · 2026 핵심 트렌드

Adaptive Quality모두에게 같은 장면을 강제하지 않는다

좌하단 HUD는 장식이 아니라 이 페이지의 실제 판정 결과다. 접속한 기기의 신호를 읽어 파티클 수, DPR 상한, 모션 여부를 조절하고 있다. 좋은 몰입형 사이트는 High/Mid/Low 티어별로 다른 장면을 서빙한다.

HIGH

WebGPU · 풀 파티클 · 포스트프로세싱 · 고해상 텍스처 · 실시간 그림자

MID

WebGL2 · 파티클 축소 · 제한적 포스트 · 베이크드 라이팅

LOW

지오메트리 단순화 · 그림자 없음 · 비디오 또는 정적 폴백

판정 중…

감지 신호

화면 크기, devicePixelRatio, 메모리, GPU 티어, 네트워크 속도, 터치 여부, WebGPU 지원, 그리고 prefers-reduced-motion. 이 페이지는 그중 다섯 가지를 실제로 읽는다.

가장 흔한 실수

setPixelRatio(devicePixelRatio)를 무조건 쓰는 것. DPR 3 폰에서 픽셀 수가 9배가 된다. 상한은 Math.min(dpr, 1.5) — 이 페이지의 모든 캔버스가 그렇게 돌고 있다.

측정 항목

웹 지표(LCP·INP·CLS)만으로는 부족하다. FPS, frame time, draw call, 텍스처 메모리, 그리고 모바일 발열과 이탈률까지 — 몰입형 사이트의 성적표는 GPU 지표를 포함한다.

SPECIMEN 11 · LAYER — PRODUCTION & ASSET

Pipeline형상은 코드 밖에서 온다

몰입형 웹은 웹 코드만으로 완성되지 않는다. 브라우저에서 실행할 수 없는 것들 — 모델링, 시뮬레이션, 텍스처 — 은 DCC 도구에서 만들어 구운(bake) 뒤 압축해서 가져온다. 이 표본은 라이브 데모가 아니라 지도다.

BLENDER / C4D / HOUDINI→ glTF / GLB→ DRACO · MESHOPT + KTX2→ CDN→ BROWSER

Blender FREE

웹 3D의 현실적 기본 도구. Geometry Nodes로 절차적 형상을 만들고 glTF로 내보낸다. AI·Python 자동화와 궁합이 가장 좋다.

Cinema 4D / Houdini

모션그래픽(C4D)과 시뮬레이션(Houdini)의 강자. 단, 웹 런타임 도구가 아니라 에셋 생성 도구 — 시뮬레이션은 캐시·텍스처·포인트 데이터로 변환해 가져온다. "C4D에서 멋졌던 장면"의 상당 부분은 웹에서 재구성이 필요하다.

glTF / GLB

웹 3D의 표준 전송 포맷. 지오메트리·머티리얼·텍스처·애니메이션·계층을 한 파일에 담는다. "3D계의 JPEG"라 불리는 이유.

Draco vs Meshopt

둘 다 메시 압축. Draco는 다운로드가 작지만 클라이언트 디코딩 비용이 있고, Meshopt는 GPU 친화적 정점 최적화를 겸한다. 파일 크기만 보지 말고 디코딩 시간과 첫 프레임까지의 시간을 측정해 고른다.

KTX2 / Basis

텍스처를 GPU가 압축 상태 그대로 쓰는 포맷. VRAM과 전송량을 동시에 줄인다. 모델보다 텍스처가 더 큰 병목인 경우가 매우 많다 — 최적화 1순위.

Spline / Rive / Lottie

디자이너 직행 루트. Spline은 3D 히어로 한 장면의 임베드에, Rive는 상태 머신 기반 인터랙티브 벡터(버튼·마스코트 — Duolingo·Spotify Wrapped가 실사례)에, Lottie는 단순 벡터 모션에. 셋 다 사이트 전체 엔진이 아니라 모듈로 쓰는 것이 안전하다.

예산 감각 BUDGET

초기 JS 500KB 이하, 초기 3D 에셋 1~3MB, 전체 3D·텍스처 5~10MB, 모바일 draw call 50~100 이하, Desktop 60fps / Mobile 30fps 안정. 고급 PC의 60fps는 성적이 아니다 — 중급 안드로이드에서 측정하라.

CMS 경계선

CMS(Sanity·Contentful·Payload)에는 제목·본문·이미지·순서만. 카메라 좌표, 셰이더 파라미터, 타임라인을 CMS에 넣는 순간 시스템은 깨진다. CMS = 콘텐츠, Code = 연출.

SPECIMEN 12 · 조합의 기술

Recipes스택은 단품이 아니라 정식(定食)이다

기술 선택의 진짜 질문은 "무엇이 최신인가"가 아니라 "누가 시간을, 공간을, 상태를 소유하는가"다. 검증된 조합 — 이 페이지 자체는 A티어 레시피로 만들어졌다.

S TIER

실무 균형형

Next.js + React Three Fiber + GSAP + Blender + glTF 최적화

운영형 브랜드 사이트의 기본기. CMS·다국어·로그인이 있다면 이쪽. 생태계와 채용, AI 코딩 도구와의 궁합까지 균형이 가장 좋다. 리스크는 React·R3F·GSAP·Lenis의 라이프사이클 충돌 — 역할 분리 원칙이 필수.

Astro + Three.js 또는 R3F Island + GSAP

대부분은 정적 HTML, 3D는 섬(island)으로 격리. 콘텐츠가 많고 히어로만 몰입형이라면 Next.js보다 이쪽이 정확하다. SEO와 초기 로드에 유리.

A TIER

Creative Coding형 THIS SITE

Vite + TypeScript + Three.js + GLSL + GSAP + Lenis

렌더 루프를 완전히 직접 통제하는 한 편의 인터랙티브 작품. 단기 캠페인, 포트폴리오, 아트 디렉션 최우선 프로젝트의 선택지. 독창성은 최고, 개발자 개인 의존도가 리스크.

A TIER

게임·공간형

Babylon.js 또는 PlayCanvas + WebGPU/WebGL + 물리 + WebXR

"페이지를 본다"가 아니라 "공간을 플레이한다"면 엔진형 접근. 가상 쇼룸, 캐릭터 이동, XR. SEO·접근성은 별도 설계가 필요하다.

B TIER

디자이너 속도형

Framer / Webflow + Spline + Rive

일주일 안의 POC, 이벤트 페이지, 개발자 없는 팀. 시각 제작 속도는 최고지만 런타임이 여러 겹이라 최적화 통제가 어렵다. 검증 후 Three.js로 재구축하는 디딤돌로 쓰는 것이 정석.

FUTURE

Generative WebGPU형

Three.js WebGPURenderer + TSL + Compute Shader + WebGL2 폴백

수십만 파티클, 실시간 유체, GPU 연산이 표현 자체에 필요할 때만. "WebGPU를 썼다"는 사실은 사용자 가치가 아니다 — 목표가 아니라 최적화 수단.

SPECIMEN 13 · 부검 기록

Anti-patterns죽은 사이트들의 공통 사인(死因)

  1. 도구 전부 넣기 GSAP + Motion + Lenis + Theatre + Spline

    각각은 좋은 도구지만 한 프로젝트에 다 넣으면 "누가 카메라를 움직이는가"의 답이 여러 개가 된다. 같은 속성을 두 라이브러리가 제어하는 순간 값은 덮어써진다. GSAP=시간, R3F=공간, React=상태, Lenis=스크롤 입력 — 소유권을 하나씩만.

  2. 전체 페이지를 Canvas로

    SEO 소멸, 접근성 소멸, 텍스트 품질 저하, 복사·링크·입력 전부 재구현. 제목과 본문은 실제 HTML로, Canvas는 aria-hidden 시각 레이어로. 이 페이지의 모든 표본이 그 구조다.

  3. 4K 텍스처와 실시간 그림자 남발

    시각 차이는 작고 VRAM·대역폭은 폭증한다. 512~2048 텍스처 + KTX2 + 베이크가 정답인 경우가 대부분.

  4. 모바일 = 데스크톱의 축소판

    모바일에는 다른 장면이 필요할 수 있다. Desktop은 인터랙티브 3D, Mobile은 축소 3D, 저사양은 비디오, reduced-motion은 정적 이미지 — 티어별 서빙이 기본.

  5. 모든 애니메이션을 스크롤에 묶기

    사용자는 스크롤을 콘텐츠 탐색에 쓴다. 모든 물체가 매 순간 반응하면 피로하고 정보 위계가 사라진다. 연출은 밀도가 아니라 배치다.
